# 비트맵 검색 엔진 실험 (Elasticsearch 대체 가능성)

이커머스 상품 검색을 겨냥한 실험용 엔진(Rust)과, 같은 데이터·같은 요청으로 Elasticsearch 9.2, Vespa 8.781과 비교한 결과입니다.

엔진의 핵심 아이디어는 세 가지입니다.

- 상품 docid를 인기 순서로 매깁니다. 그래서 인기순 top-k는 조건을 만족하는 문서를 앞에서부터 k개 찾으면 끝납니다(조기 종료).
- 카테고리, 재고, 가격 구간, 제목 단어를 모두 비트맵이나 posting으로 둡니다. 재고·가격 갱신은 비트 하나를 바꾸는 일이 됩니다.
- 카탈로그 전체를 노드 하나의 메모리에 둡니다(샤드 분배·병합 없음).

> 결론부터: 편향을 제거하고 비교하면 **필터·인기순 검색과 재고·가격 갱신은 우리 엔진이 앞서고, 필터가 붙은 BM25와 정확한 facet은 ES(1샤드)가 같거나 앞섭니다.**
> 초기에 주장했던 "7~14배"는 ES 과다 샤딩, 튜닝에 쓴 쿼리로 보고한 것 등 측정 오류가 섞인 수치였습니다([아래](#이전-주장-중-틀렸던-것)).

## 재현 방법

### 데이터

Hugging Face `McAuley-Lab/Amazon-Reviews-2023`의 `raw/meta_categories/meta_Electronics.jsonl`, `meta_Cell_Phones_and_Accessories.jsonl`을 스트리밍으로 받아 TSV로 만듭니다(합계 2,898,337건).

```bash
for c in Electronics Cell_Phones_and_Accessories; do
  curl -sSL "https://huggingface.co/datasets/McAuley-Lab/Amazon-Reviews-2023/resolve/main/raw/meta_categories/meta_$c.jsonl" \
    | python3 -I extract_amazon.py > amazon/$c.tsv
done
cat amazon/Electronics.tsv amazon/Cell_Phones_and_Accessories.tsv > amazon/all.tsv
```

데이터셋에 없는 재고(`stock`, 90%)와 로켓배송(`rocket`, 40%) 필드는 docid로 결정되는 합성값입니다.

### 빌드

```bash
# rdkafka(cmake-build)용 시스템 패키지
apt-get install -y cmake libcurl4-openssl-dev libssl-dev zlib1g-dev libzstd-dev liblz4-dev libsasl2-dev pkg-config
cd engine && RUSTFLAGS="-C target-cpu=native" cargo build --release
```

### Elasticsearch 9.2.0

- root로 실행할 수 없으므로 별도 사용자(`es`)로 실행합니다. 설정: 단일 노드, 보안 끔, 힙 4 GB.
- 이 컨테이너는 디스크 사용률이 높게 계산되므로 워터마크를 절대값으로 지정해야 합니다.
  `cluster.routing.allocation.disk.watermark.{low,high,flood_stage}` = `3gb`, `2gb`, `1gb`.
- 적재: `SHARDS=1 es realload amazon/all.tsv`. 적재 후 `refresh_interval`을 1s로 되돌리고 force merge합니다.

### 편향 제거 비교

```bash
taskset -c 1-3 target/release/prod amazon/all.tsv proddata &      # 엔진 서버(포트 9400)
taskset -c 0 target/release/es faircheck amazon/all.tsv           # 세 시스템 결과 교차 검증
SPID=<서버 pid> taskset -c 0 target/release/es fair ours amazon/all.tsv
SPID=<ES pid>   taskset -c 0 target/release/es fair es   amazon/all.tsv
taskset -c 0 target/release/es oos es amazon/all.tsv              # 상관된 품절 상태 반영
```

HTTP 서버에는 `TCP_NODELAY`가 반드시 필요합니다. 빠지면 Nagle과 delayed ACK 때문에 응답마다 약 40 ms가 걸립니다.

## 결과: 편향을 제거한 비교

조건은 다음과 같습니다.

- 실제 상품 2,898,337건, 4 vCPU 한 대
- 서버는 코어 1~3, 클라이언트는 코어 0에 고정
- ES는 1샤드(이 크기 인덱스에 맞는 설정), 측정 전 예열
- 쿼리는 튜닝에 쓰지 않은 held-out 세트: 상품을 균일하게 뽑은 세트와 인기 하위 50%(롱테일)에서 뽑은 세트, 각 300개씩
- 모든 응답이 문서 원문(`_source`/summary)을 포함

### 결과 일치 (속도 비교의 전제)

| 항목 | ES (1샤드) | Vespa |
|:--|--:|--:|
| 필터 + 인기순 top-10 | 900/900 일치 | 900/900 일치 (`match-phase`) |
| BM25 (+재고, +카테고리&재고) | 점수 500/500 일치 (갱신 전) | top-10 겹침 91~95% (`weakAnd`, 근사) |
| 브랜드 facet top-20 | 정확값 300/300 일치 | `precision` 지정 시 300/300 일치 |

갱신 후에는 ES BM25 점수가 정확값과 달라집니다. 삭제 표시된 이전 버전 문서 656,350건이 병합 전까지 BM25 통계(N=3,554,528)에 남기 때문입니다.

### 성능

| 항목 | 우리 엔진 | ES 1샤드 | ES 4샤드 | Vespa |
|:--|--:|--:|--:|--:|
| 필터 검색 처리량 (16 클라이언트) | **10,700~11,500 QPS** (클라이언트 코어 99%, 서버 55~59%) | 3,460~3,700 QPS (서버 85%) | 1,940~2,170 QPS | 715~800 QPS |
| 필터 검색 단일 p50 | **0.39~0.51 ms** | 1.7~2.2 ms | 2.2~2.6 ms | 3.5~4.4 ms |
| 품절 갱신 후 필터 처리량 | **10,700~11,300 QPS** (변화 없음) | 2,240~2,340 QPS (-35%) | - | 750~800 QPS |
| BM25 + 필터 처리량 (held-out) | 734~857 QPS | **833~974 QPS** | 673~688 QPS | 331~445 QPS (근사) |
| BM25 + 필터 단일 p99 (held-out) | 28~31 ms | **13~16 ms** | 9~11 ms | 40~67 ms |
| 브랜드 facet (정확값) p50 | 2.2~2.7 ms | **1.3~1.5 ms** | 1.6~2.0 ms | 21~39 ms |
| 재고 일괄 갱신 (2,898,337건) | **1.0 s** | 148 s | - | 582 s |

- **우리 엔진의 필터 처리량은 클라이언트 병목입니다.** 클라이언트 코어 1개가 99% 바쁜 동안 서버는 3코어의 55~59%만 썼습니다. 서버 용량은 선형 추정으로 약 1.9~2.1만 QPS이고, ES 1샤드 용량은 약 4,100 QPS입니다. 따라서 필터 검색은 실측 약 3배, 용량 기준 약 5배입니다.
- **사전 계산 비용:** 290만 건 기준 전체 빌드 15~18초입니다. posting·속성 비트맵 7.4초, BM25 통계 6.8초(그중 block-max 3.1초), facet 후보 브랜드 4.3초입니다. 재고·가격 갱신에는 영향을 받지 않고, 제목·카탈로그가 바뀔 때 다시 만들어야 합니다. 신규 상품의 증분 추가는 아직 구현하지 않았습니다.
- **WAL 재생:** 재시작할 때 2,898,337건(143 MB)을 1.3초에 재생했고, 재생 후 결과가 ES와 300/300 일치했습니다.
- **RAM:** 엔진은 인덱스 전체를 메모리에 둡니다(상품당 약 96 B, 문서 원문은 디스크). ES는 디스크와 페이지 캐시로도 동작하므로, 같은 RAM 예산이라면 결과가 달라질 수 있습니다(측정하지 않음).

| 이전 주장 | 실제 | 원인 |
|:--|:--|:--|
| 필터 검색 7~14배 | 실측 약 3배, 용량 기준 약 5배 | ES를 4샤드로 나눔(1샤드보다 약 40% 느림), 클라이언트와 서버가 CPU를 공유 |

## 이번 목표: 필터 인식 BM25

필터가 붙은 BM25에서 진 원인은, 필터를 후보 문서마다 사후에 확인하는 구조였습니다. ES는 필터를 교집합 반복자로 함께 순회합니다.
이를 고친 뒤의 판정은 아래 [필터 인식 BM25 판정](#필터-인식-bm25-판정)에 기록합니다.

## 필터 인식 BM25 판정

### 바꾼 것

`realcat.rs`의 `bm25_shards_f`를 고쳤습니다.

- **필터를 순회 안으로:** 필터(카테고리, 재고, 가격 구간)를 후보마다 사후에 확인하지 않고, MaxScore/block-max 순회 안의 leapfrog 커서로 넣었습니다.
  - 후보 docid를 고르면, 필터마다 그 docid 이상인 다음 문서를 찾습니다.
  - 그 문서가 더 뒤에 있으면 단어 posting들을 거기까지 `advance_to`로 건너뜁니다.
  - 필터가 선택적일수록 이 건너뛰기가 커져서, 필터 비트맵을 드라이버로 쓰는 것과 같은 효과가 납니다. 그래서 별도 경로는 만들지 않았습니다.
- **후보당 오버헤드 제거:** 구간 상한 버퍼를 재사용하고, 같은 128-docid 구간 안에서는 block-max 상한을 다시 계산하지 않습니다.
- **임계값은 바꾸지 않았습니다.**
- **개발과 보고 분리:** 개발과 튜닝은 dev 세트(seed 400/500)로만 했습니다. 판정은 **한 번도 보지 않은 새 held-out 세트(seed 600/700, 유형당 500개)** 로, 측정 전에 조건을 정해 두고 했습니다.

### 정확성

| 확인 | 결과 |
|:--|:--|
| 전수 계산(`bm25_exhaustive_f`)과 비교 (dev 1,000개, id와 점수) | **1,000/1,000 일치** |
| 새로 적재한 ES 1샤드와 top-10 점수 (판정용 새 세트, 갱신 전) | **2,000/2,000 일치** |
| 기존 held-out 세트에서 ES와 비교 (필터 900, BM25 500, facet 300) | 전부 일치 |

### 성능 (판정용 새 세트, 2회 반복, 측정 순서를 바꿔 가며)

조건은 서버 코어 1~3, 클라이언트 코어 0, ES 1샤드에 `refresh_interval` 1s, 두 번 예열입니다. 두 서버 모두 3코어의 97~99%를 썼고, 클라이언트 코어는 23~32%만 써서 병목이 아니었습니다.

| 세트 / 쿼리 | 우리 엔진 처리량 (1회 / 2회) | ES 1샤드 처리량 | 우리 단일 p99 | ES 단일 p99 |
|:--|--:|--:|--:|--:|
| uniform, BM25 + 재고 | **2,017 / 2,015 QPS** | 1,075 / 990 | **7.9 / 6.5 ms** | 15.6 / 14.2 ms |
| uniform, BM25 + 카테고리 + 재고 | **1,754 / 1,833 QPS** | 1,343 / 1,371 | **8.4 / 10.9 ms** | 11.4 / 11.0 ms |
| long-tail, BM25 + 재고 | **2,059 / 2,124 QPS** | 972 / 986 | **9.9 / 6.7 ms** | 18.8 / 18.6 ms |
| long-tail, BM25 + 카테고리 + 재고 | **1,907 / 1,933 QPS** | 1,420 / 1,451 | **9.0 / 8.9 ms** | 9.6 / 9.8 ms |

16 클라이언트 p99는 우리 엔진 17~21 ms, ES 28~45 ms였습니다.

### 판정: 성공 기준 충족 → ES 전면 대체 방향 유지

8개 칸(세트 2 × 쿼리 2 × 반복 2) 모두에서 16 클라이언트 처리량과 단일 p99가 ES 1샤드 이상입니다. 다만 차이의 크기는 쿼리 유형에 따라 다릅니다.

- **BM25 + 재고:** 처리량 약 1.9~2.2배, 단일 p99 약 2~2.8배 낮습니다. 확실한 우위입니다.
- **BM25 + 카테고리 + 재고:** 처리량은 1.30~1.34배로 앞섭니다. 하지만 단일 p99는 4칸 중 3칸이 거의 동률입니다(8.9 대 9.6, 10.9 대 11.0, 9.0 대 9.8 ms). 이 유형의 단일 지연은 "앞선다"보다 "같은 수준"이 정확합니다.

### 판정 과정에서 드러난 것 (불리한 결과 포함)

- **최적화 전에는 기준을 못 넘었습니다.** 필터 커서만 넣은 상태에서 기존 held-out 세트(seed 200/300)를 2회 측정했더니, 처리량은 4칸 모두 앞섰습니다. 하지만 2회차 long-tail BM25 + 카테고리 + 재고의 단일 p99가 **10.2 ms 대 ES 8.8 ms로 기준 미달**이었습니다(`results/fair_bm25_split_rep2.log`). 후보당 오버헤드를 dev 세트로만 줄인 뒤, 새 세트로 다시 판정했습니다.
- **같은 쿼리여도 ES 측정값이 실행마다 10~20% 흔들렸습니다.** 예를 들어 같은 세트의 BM25 + 필터가 833~974 QPS였다가 1,031~1,188 QPS로 나왔습니다. 그래서 2회 반복하고 순서를 바꿨습니다.
- **ES가 여전히 앞서는 영역:** 정확한 facet입니다. ES 1샤드는 p50 1.3~1.9 ms, 우리 엔진은 2.0~2.7 ms입니다. 이번 목표(BM25)와는 별개로 남은 격차입니다.

## 분산 구조 시험

### 방식

4 vCPU 머신 한 대에서 노드를 별도 프로세스로 띄웠습니다.

- **노드 배치:** 노드마다 코어 1개(1~3)를 고정했습니다. 클라이언트는 코어 0에 고정했습니다.
- **네트워크:** 노드 사이는 loopback입니다. 실제 네트워크 지연, 패킷 손실, 네트워크 분할은 들어가지 않았습니다.
- **노드 (`engine/src/bin/node.rs`):** docid 범위 `[lo, hi)`만 색인합니다. 쓰기는 직접 받지 않고 공유 갱신 로그를 tail해서 반영합니다.
  - 복제본은 전체 범위, 파티션은 인기 구간 3등분입니다.
  - BM25 통계(df, N, avgdl, block-max)는 파티션도 카탈로그 전체 기준으로 계산하므로, 파티션의 점수가 단일 노드와 같습니다.
- **라우팅 (`engine/src/bin/distbench.rs`):** 클라이언트가 직접 합니다(smart client).
  - 복제본 사이에서는 round robin으로 보냅니다. 오류가 나면 같은 노드에 즉시 1회 재시도하고, 그래도 실패하면 500 ms 동안 그 노드를 빼고 다른 복제본으로 보냅니다(circuit breaker). 헬스 체크는 100 ms마다 합니다.
  - 파티션에는 scatter-gather를 쓰고, 인기순 정렬에는 앞 파티션부터 묻는 tiered 방식도 씁니다.
- **쓰기:** 공유 로그 파일(Kafka 대용)에 1,000건 묶음 단위로 append한 뒤 fsync합니다. 노드는 묶음이 다 들어오면 적용합니다.
- **일관성 검증:** 클라이언트가 초기 상태에 자신이 쓴 갱신을 직접 적용해 기대 상태를 계산합니다. 각 노드의 `(재고, 가격)` digest와 대조합니다.
- **쿼리:** 판정용 새 held-out 세트(seed 600/700)를 썼습니다.

### 시험 중에 발견하고 고친 버그

- **`apply_batch`가 불안정 정렬을 썼습니다.** 한 묶음 안에 같은 상품의 재고 갱신이 두 번 있으면 순서가 바뀔 수 있었습니다. 정렬이 결정적이라 세 복제본은 서로 같은 상태였지만, **로그 순서와는 다른 상태**였습니다. 클라이언트가 계산한 기대 상태와 대조하면서 발견했고, 안정 정렬로 고쳤습니다.
  이전의 합성 데이터 primary/replica 시험("digest 일치")도 양쪽이 같은 정렬을 써서 이 문제가 가려져 있었습니다.
- **라우터가 오류 한 번으로 노드를 영구 제외했습니다.** 첫 T1 측정이 이 때문에 무효였고, circuit breaker와 같은 노드 1회 재시도로 고쳤습니다.

### 분산 시험의 한계 (T1~T4 시점)

T1~T4는 loopback, 공유 로그 파일, 전체 재빌드, 노드 3개 조건이었습니다. 아래 "운영 장애 시험"에서 이 네 가지를 다시 시험했습니다.

## 운영 장애 시험: Kafka, 스냅샷, 네트워크 장애, 노드 6개

### 방식

- **복제 로그:** Kafka 4.4.0 KRaft 브로커 3개를 띄웠습니다(`results/cluster/kafka_conf/`). 설정은 RF 3, `min.insync.replicas=2`, producer `acks=all` + idempotent이고, 1,000건 묶음 하나를 메시지 하나로 보냅니다. 브로커는 노드와 같은 코어 1~3에 고정했습니다.
  - 노드는 파티션 0을 지정 offset부터 읽고, 묶음 번호(seq)로 중복을 버립니다(`dups`, `gaps` 카운터).
  - Kafka 기본값이라 메시지마다 fsync하지 않습니다. 내구성은 복제(ISR 2개 이상)에 기대는 것이며, 로그의 "fsync per batch" 문구는 파일 로그용 출력이 그대로 남은 것입니다.
- **스냅샷:** 노드가 `/_snapshot` 요청을 받으면 묶음과 묶음 사이에 인덱스, 어휘 사전, Kafka offset을 디스크에 씁니다. 재시작 시 `SNAP_LOAD`로 읽고 그 offset부터 로그를 재생합니다.
- **네트워크 장애:** 이 커널에는 netem이 없어서 userspace TCP 프록시(`engine/src/bin/faultproxy.rs`)를 노드 앞에 두었습니다. 설정 파일을 50 ms마다 다시 읽고 다음을 겁니다.
  - 지연: 전달하는 chunk마다 지연 + 지터.
  - 손실 대용: 일정 확률로 chunk를 수백 ms 멈춥니다. 재전송 지연을 흉내낸 것이고, 실제 패킷 손실은 아닙니다.
  - 연결 거부(refuse)와 blackhole(받기만 하고 응답 안 함, 조용한 네트워크 분할).
- **라우터 (`HRouter`):** 요청 타임아웃, 다른 복제본 1회 재시도, 선택적 hedged request, 선택적 staleness 회피(쓰기보다 10묶음 넘게 뒤처졌거나 준비 안 된 복제본 제외, 50 ms마다 표본)를 지원합니다.
- **일관성:** K1~K3은 클라이언트가 계산한 기대 상태 digest와 대조했고, N4는 6개 복제본의 digest가 서로 같은지 확인했습니다.

```bash
K=kafka:127.0.0.1:19091,127.0.0.1:19092,127.0.0.1:19093/updates
# 노드 (복제본: LO=0), 스냅샷에서 시작하려면 SNAP_LOAD=<dir>
taskset -c 1-3 node amazon/all.tsv cluster 9501 $K 0
# 프록시: 9701 -> 9501, 장애 설정은 faults/9701.conf ("normal|refuse|blackhole lat_ms jitter_ms stall_prob stall_ms")
faultproxy 9701 9501 faults/9701.conf
# K1/K2/K3: writes / failover 모드 (KILL_BROKER, SNAPDIR, KILL_PID, RESTART_CMD 환경변수)
taskset -c 0 distbench writes amazon/all.tsv 9501,9502,9503 $K 50000
# N1~N3 (NF_PHASES=123), N4
taskset -c 0 distbench netfault amazon/all.tsv 9701,9702,9703 9801,9802,9803 faults $K
RESTART_CMD="..." taskset -c 0 distbench multifault amazon/all.tsv 9701,9702,9703,9704,9705,9706 faults $K 200 0
```

**K3 스냅샷 재시작** (쓰기 계속, 7초에 스냅샷, 12초에 `kill -9`, 27초에 재시작)

| | 스냅샷 재시작 | 전체 재빌드 (T3) |
|:--|--:|--:|
| 합류까지 | **1.5초** (로드 0.4초 + 로그 재생) | 48초 |
| 재시작 후 RSS | 453 MB | 1,080 MB |

- 스냅샷은 290 MB, 2.1초 걸렸습니다. **그동안 그 노드는 로그 적용을 멈추므로** 지연이 최대 2초(102묶음)까지 커졌습니다. 운영에서는 스냅샷을 찍는 노드를 라우팅에서 빼야 합니다(아래 N3의 staleness 회피가 그 역할).

**N1 hop마다 네트워크 지연** (클라이언트 8스레드, 15초씩)

| 지연 조건 | 복제본 3개 BM25 | 복제본 3개 필터 | 파티션 scatter BM25 | 파티션 scatter 필터 | 파티션 tiered 필터 |
|:--|--:|--:|--:|--:|--:|
| 없음 | 1,485 QPS, p99 29.5 | 7,253, p99 4.2 | 1,112, p99 21.7 | 2,861, p99 7.9 | 7,393, p99 3.3 |
| 0.5 ms + 지터 1 ms | 1,238, p99 23.5 | 2,189, p99 5.8 | 576, p99 37.7 | 671, p99 32.7 | 1,685, p99 12.1 |

- **scatter-gather는 지연에 가장 약합니다.** 파티션 3개 중 가장 느린 응답을 기다리므로, 1% 정지가 p99 466~501 ms로 커졌습니다. tiered는 대부분 파티션 하나만 묻기 때문에 복제본과 비슷했습니다.
- 지연이 생기면 필터 쿼리의 처리량이 크게 떨어집니다(7,253 → 2,189). 클라이언트 스레드 8개가 왕복 시간 동안 기다리기 때문이며, 동시 요청을 늘리면 회복될 것으로 봅니다(시험 안 함).

**N2 복제본 하나를 10~25초 blackhole** (쓰기 초당 50,000건 계속, 40초)

| 라우터 설정 | 분할 중 처리량 | 분할 중 p99 | 실패 |
|:--|--:|--:|--:|
| 타임아웃 10초, hedge 없음 | **45 QPS** | 25.6 ms (끝난 요청만) | 16 |
| 타임아웃 200 ms, 재시도 | 664 QPS | 208 ms | 0 |
| 타임아웃 2초, 20 ms hedge (수정 후) | 580 QPS | 39.6 ms | 0 |

- **타임아웃 10초 설정은 사실상 서비스 중단입니다.** blackhole은 연결을 끊지 않으므로 오류가 나지 않고, 그 복제본으로 간 요청이 10초씩 기다리며 클라이언트 스레드를 묶습니다. circuit breaker는 500 ms 뒤 다시 그 노드를 시도하므로 같은 일이 반복됩니다.
- **hedge의 첫 구현은 실패했습니다**(분할 중 88 QPS, p99 1.73초, `n_netfault.log`). hedge가 이겨도 느린 primary를 표시하지 않아, 모든 요청이 계속 blackhole 노드로 먼저 갔습니다. hedge가 이기면 primary를 500 ms 제외하도록 고친 뒤 다시 측정한 것이 위 표입니다(`n2_rerun.log`).
- **hedge는 정상 구간 처리량을 낮췄습니다.** 정상 구간이 677 QPS로, 같은 실행에서 hedge 없는 설정(1,111 QPS)보다 낮았습니다. 첫 실행에서는 941 QPS였습니다. 원인은 확인하지 못했습니다.
- 가장 나은 설정은 짧은 타임아웃(200 ms)과 재시도였습니다. 대가는 분할 중 p99 ≈ 타임아웃(208 ms)입니다.

**N3 복제본 하나가 10~25초 로그 적용을 멈춤** (쓰기 계속)

- 노드와 Kafka 사이의 분할을 흉내낸 것입니다(`/_pause`). Kafka가 advertised listener 주소를 클라이언트에 돌려주므로 프록시를 거치게 할 수 없었습니다.
- **staleness 회피가 없으면 읽기의 32.7%가 10묶음 넘게 뒤처진 복제본에서 나왔습니다.** 가장 오래된 것은 746묶음(약 15초) 전 상태였습니다. 오류는 없으므로 라우터는 이를 알 수 없습니다.
- staleness 회피를 켜면 그런 읽기가 1건(0.0%), 가장 뒤처진 것이 12묶음이었습니다. 처리량은 분할 구간에서 864 QPS(회피 없음 942 QPS)였습니다.

**N4 복제본 6개, 장애 4개 중첩** (60초, 쓰기 초당 50,000건 계속, 타임아웃 200 ms + 재시도 + staleness 회피)

장애 일정:
- 10~30초: :9702 blackhole
- 15초: :9504 `kill -9`, 35초에 스냅샷에서 재시작
- 20~45초: :9705에 지연 1 ms + chunk 2%가 300 ms 정지
- 20~40초: :9506 로그 적용 정지

| 구간 | 처리량 | p50 / p99 | 최대 | 실패 | 뒤처진 복제본에서 읽음 |
|:--|--:|--:|--:|--:|--:|
| 정상 (0~10초) | 940 QPS | 5.2 / 45.7 ms | 102 ms | 0 | 6건 (0.1%) |
| 장애 1개 (10~15초) | 673 | 5.8 / 206 | 237 | 0 | 0 |
| 장애 2개 (15~20초) | 656 | 6.0 / 208 | 247 | 0 | 0 |
| 장애 4개 (20~30초) | 689 | 5.7 / 207 | 239 | 0 | 0 |
| 장애 3개 (30~35초) | 1,071 | 4.6 / 34.6 | 231 | 0 | 0 |
| 재시작 + 2개 (35~45초) | 759 | 5.9 / 53.7 | 236 | 0 | 0 |
| 복구 (45~60초) | 923 | 4.9 / 45.1 | 84 | 0 | 0 |

- **실패한 요청은 0건입니다.** 재시도는 289건이었습니다.
- **쓰기를 멈추고 4.5초 안에 6개 모두 24,005묶음에 도달했고, digest가 모두 같았습니다.** 중복과 누락은 0건입니다.
- 재시작한 노드는 28.4초 만에 준비되었습니다. 스냅샷이 offset 253에 찍힌 오래된 것이라 약 21,000묶음(2,100만 건)을 재생했기 때문입니다. 재생 중에는 staleness 회피로 그 노드에 읽기가 가지 않았습니다.
- 정상 구간의 뒤처진 읽기 6건은 측정 시작 직후 표본이 아직 없을 때 나온 것으로 보입니다.
- **blackhole이 있는 동안 p99는 타임아웃(200 ms)에 묶입니다.** 그 노드로 가는 요청이 500 ms마다 다시 시도되기 때문입니다. 더 줄이려면 연속 실패에 따라 제외 시간을 늘리는 방식이 필요합니다(구현 안 함).
- 처리량 절대값은 노드 6개와 브로커 3개가 코어 3개를 나눠 쓰므로 T1과 비교할 수 없습니다.

### 운영 장애 시험의 한계

- **여전히 머신 한 대입니다.** 노드 6개, 브로커 3개가 코어 3개를 나눠 씁니다. 노드를 늘려도 처리량은 늘지 않으며, 이 시험은 정확성과 가용성만 봅니다.
- 네트워크 장애는 userspace 프록시로 흉내냈습니다. 실제 패킷 손실, 재정렬, 대역폭 제한은 아닙니다.
- 노드와 Kafka 사이의 분할은 `/_pause`로 흉내냈고, 실제 Kafka 소비자 재연결 경로는 시험하지 않았습니다.
- Kafka 브로커 사이의 네트워크 분할, 디스크 장애, 메시지당 fsync는 시험하지 않았습니다.
- 스냅샷은 수동으로 찍었습니다. 주기적인 스냅샷과 Kafka 보존 기간에 따른 로그 절단은 구현하지 않았습니다.
- 쓰기 writer는 하나입니다. 여러 writer 사이의 순서와 중복 제거는 Kafka idempotent producer에 맡겼고, 따로 시험하지 않았습니다.

### 이 판정의 한계

- 성능 판정은 단일 노드, 290만 건, 4 vCPU에서 측정했습니다. 5억 건 규모는 검증하지 않았고, 다중 노드는 머신 한 대 안에서 정확성과 가용성만 시험했습니다.
- ES 설정은 문서화된 범위 안에서 했습니다(1샤드, force merge, 인덱스 정렬). Lucene 전문가 수준의 튜닝을 거친 결과는 아닙니다.
- 우리 엔진은 ES 기능 중 일부만 지원합니다. 비교는 두 시스템이 같은 결과를 내는 쿼리에서만 했습니다.
- 인덱스 전체를 RAM에 두는 비용(상품당 약 96 B)은 위 수치에 반영되지 않았습니다.
